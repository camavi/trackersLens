# TL MCP Server

Purpose: external assistant access to the open TL project, independent of Flow Chat.
Read when: changing the MCP server, local connection or external TL control.
Last updated: 2026-10-21.

## Product direction

External editors/assistants edit project files. TL executes its runtime and exposes its own state, output and errors. TL is not a file-change surveillance system. The existing Chat remains available; expansion toward full IDE parity is no longer the active direction. The existing MCP client is separate from this MCP server.

## Initial connection boundary (apply extension below)

Project menu → MCP del progetto → Attiva MCP. The service is disabled by default and must be enabled again in each project session. It grants local processes of the same OS user read access to the open project's persisted graph, configuration, channel output and runtime logs. No account/profile/provider credentials or arbitrary stores are exposed as tools. Authorized runtime data may itself contain sensitive content; the enable dialog describes this scope.

Main owns `LocalMcpService`, its project identity and persistence adapter. Named `desktop.mcpServer.status/start/stop` commands require the trusted main frame/session and an open project. Project exit stops the service and disconnects clients before shutdown. Concurrent start/stop operations serialize. No service is started implicitly by an external client.

The external client starts `node scripts/tl-mcp.cjs --project /absolute/project`; the script is a standards-based MCP stdio server using the official `@modelcontextprotocol/sdk` 1.32.1. Its private local transport connects to the already-open TL process, whose service publishes schemas and executes named tools. stdout contains MCP messages only. The complete client configuration is shown in the project dialog; the generic mcpServers envelope may need adapting to the client configuration format. This first distribution assumes a source checkout, dependencies installed and Node on the external client's PATH; a packaged standalone CLI remains separate work.

Local transport uses a Unix socket beneath `.tl/mcp` (0700 directory, 0600 socket/descriptor). Directory/descriptor symlinks are rejected. Socket names are per-instance; the descriptor is atomically replaced and removed only by its owning instance. Client disconnect rejects pending reads without replay. There are no TCP listeners, remote HTTP/OAuth endpoints or implicit network exposure. Initial local transport supports macOS/Linux; Windows named pipes remain open work. Stale private descriptors after a crash do not grant access to a closed service; enabling creates a new instance/socket.

## Tools

- `tl_get_project`: connected project identity and explicit capability flags.
- `tl_list_flows`: existing `readFlowMapLibraryIndex` summaries, with no MCP pagination/truncation.
- `tl_inspect_workspace`: full persisted graph/channel/flow records and Flow Map document for an exact workspace.
- `tl_inspect_node`: exact workspace node and incident dependency/connection records.
- `tl_read_channel`: exact full persisted channel output.
- `tl_read_runtime_events`: all persisted events and Flow logs for the requested workspace.
- `tl_preview_node_edits`: existing Core `planNodeEdits` validation for rename/move/config with full before/after, without writes, approval token or activation.

Schemas are validated in the TL process as well as negotiated through MCP. The tool service cannot dispatch generic SQL, filesystem writes, process execution or arbitrary Core commands. The following reviewed-apply extension adds two explicitly declared tools while keeping reads annotated read-only. Explicit exact-workspace guards protect node/channel lookup. Responses identify persisted-state provenance and observation time. Separate store reads do not constitute an atomic cross-store or live renderer/worker snapshot; unsaved runtime output may be absent. No MCP-owned output caps are added.

## Reuse and remaining work

Core persistence, Flow library indexing and the registered node-edit planner are reused. Applying graph edits must retain registered-tool routing, revalidation, snapshots, durable receipts and renderer/worker reconciliation before it becomes available externally. Core-owned creation/palette authority and package lifecycle commands must be designed without trusting arbitrary client-supplied manifests/records. Runtime start/stop must connect to actual execution controllers; the existing Agent Runtime runFlow trace-only API must never be presented as real execution. These operations are not provided by the initial server.

## Reviewed existing-node application (2026-10-21)

`core/mcp/node-edits.cjs` delegates preview and apply to the existing registered `desktop.flowChat.applyNodeEdits` Core path. Only rename/move/config operations on exact existing nodes are currently accepted. Preview returns full before/after plus a server-generated planId and operationId. Plans are bound to the private local socket connection and cannot be supplied or reconstructed by another connection.

`tl_apply_node_edits({planId})` requires local TL approval for the exact preview. Main sends a one-use owner-bound review to the trusted renderer; the JSswift dialog shows complete changes/before/after. Approval cannot be forged through MCP arguments. A denied result performs no writes. Disconnect cancels pending review and forgets plans. Main serializes apply and rejects project transitions or active persisted/native work before editor suspension. Core independently rejects stale before-state, active nodes/jobs and invalid final configuration.

After approval, Main uses the existing project-close preparation to blur/flush pending edits and stop/drain view work, then unloads the editor to a script-free holding page. It commits only through the atomic Core path and reloads app.html so stale in-memory graph state cannot overwrite the result. Idle checks are repeated after suspension. The current approach reloads the full editor and may close ephemeral editor-bound sessions; it is not hot in-place reconciliation. Snapshot/receipt commit and renderer loading are separate operations. If reload fails, the client receives an error and must inspect the durable receipt before considering another action.

`tl_get_edit_receipt({workspaceId,operationId})` reads the existing durable Core receipt for an MCP-generated operation. A repeated apply of a committed plan returns its receipt without replaying the mutation or opening another review. A new connection can recover an exact known operationId but cannot reuse an old preview. Receipt absence does not authorize automatic retry: prepare and review a fresh plan. Receipt presence proves the SQLite mutation/snapshot, not successful visual reload or actual runtime execution.

Production `LocalMcpService` advertises nine tools and applyNodeEdits=true; standalone test/read adapters without mutation integration retain the seven-tool read-only surface. Existing tools still return full persisted output. Runtime start/stop, graph creation/connection/deletion and package installation are not exposed by this extension.

## Exact links and duplication (2026-10-21)

`tl_preview_graph_edits({workspaceId,edits})` accepts only exact `connect`/`disconnect` operations with sourceNodeId/targetNodeId/sourcePort/targetPort, and `duplicate` with nodeId/value (new label) and optional numeric position. It is available only when the mutation coordinator is integrated. Schemas reject provider-supplied dependencyId/connectionId/newNodeId and arbitrary node manifests. `McpNodeEdits.previewGraph` allocates these identities once inside TL and returns normalized edits for inspection. The external client applies the returned planId using the same tl_apply_node_edits and local review. The tool catalog now contains ten tools.

Core validates existing ports and exact workspace targets, prevents duplicate/missing links and checks the entire scoped graph against reviewed before-state at commit. Full graph before/after includes channels/flows/dependencies/connections; later channel-output changes reject the plan rather than overwrite runtime data. Existing Core cross-workspace/global-ID/package/busy guards remain authoritative. New duplicate instances derive from an existing node, start idle/inactive and preserve its validated configuration/package reference. No client-supplied palette definition is accepted. Existing shared-channel producers are preserved and the full Core warning remains visible.

Disconnect removes only matching dependency/connection/Flow references; channel values, historical events and runtime logs remain. Connect/disconnect is not a subscription/start/stop command and never implies execution. Duplication provides creation from an existing validated instance; creation from a fresh palette template, deletion and restoration tools remain separate work. Normalized edit IDs and durable receipts prevent duplicate application after a lost reply.

Acceptance extends the official MCP client test through connect → repeat receipt → disconnect → inactive duplicate, with undeclared/foreign/invalid-port rejection, complete output preservation and stale-channel CAS. Production Electron exercises local approvals and editor reload for all three operations. No live-model selection claim is made.

## Installed single-node execution (2026-10-21)

Four named tools extend the production catalog to fourteen tools: `tl_preview_run_node({workspaceId,nodeId,inputs})`, `tl_start_node_run({planId})`, `tl_get_node_run({runId})`, `tl_stop_node_run({runId})`. Preview requires an exact persisted node with a sandboxed Custom Node package reference; the existing package manager validates installed activation, consent, archive and source. Plans bind node/config/package/source hashes and exact inputs to one local connection. Local TL review exposes node/config, package reference, declared/granted permissions and execution metadata. No inline code, arbitrary program/process command or inferred install is accepted.

After approval, Core revalidates source and checks connection cancellation again before recording a run and starting the same Main-owned Custom Node runner already used by TL. A consumed plan cannot start another execution; its runId remains available for evidence recovery. Inputs are the declared sandbox input map (for example `{input:{value:4}}`), not an implicit event-bus publication. This is one-shot node execution: it does not emit into downstream Flow subscriptions, activate the persisted node or claim whole-Flow completion. Actual runtime results/logs are kept in the run, not silently merged into graph channels.

The coordinator owns abort controllers and complete `tl_ai_jobs` records with kind mcp-node-run. State includes starting/running/terminal evidence, executionId, full input/output/diagnostics/raw broker trace, timestamps and duration. `get` includes live broker events during execution and the saved full trace after completion. Persistence errors are exposed instead of inventing success. A recovered record marked running without a live owner is reported interrupted/unknown-after-restart and never rerun. Current APIs recover an exact disclosed runId; a broader run-history discovery UI/tool remains separate work.

Stop requires the owning connection, aborts the real runner and waits for cleanup before returning cancelled. It does not undo prior tool side effects. Disconnect cancels that owner's pending reviews and active runs; disabling MCP/project shutdown destroys client sockets then drains owned runners. Main maps cancellation to EXECUTION_CANCELLED before closing Electron sandbox windows or Python children; Python close now returns a Promise resolved on child close. Existing package timeout configuration remains authoritative; MCP adds no implicit duration/output cap. JavaScript sandbox acceptance is verified; Python through this MCP path is not yet independently accepted.

The client also controls approval of non-read-only/open-world tools. The real Codex test required explicit per-tool client approval settings for start/stop in its dedicated invocation; TL's local approval remained required. An initial noninteractive-client rejection occurred before any execution and was not an application runtime failure. Do not mislabel these tools as read-only to avoid client approvals.

`test/tl-mcp-runtime.test.cjs` covers scope, exact-source freshness, consumption, live reports, owner stop/disconnect, disconnect during asynchronous revalidation and historical interrupted-state recovery. `test/tl-mcp-runtime-electron.cjs` installs/activates only a temporary QA package and uses the actual SDK client/Main/sandbox: 4→8, invalid-number error, 5→10, then a waiting execution with live log and real window termination. Separate graph Electron regression remains passing.

Real external Codex acceptance used seventeen MCP calls and four local TL approvals. Independent SQLite checks confirm four distinct completed/failed/completed/cancelled runs, preserved failure, outputs 8/10, actual cancellation diagnostic, durations and unchanged node/archive. The driver asserts no sandbox window survives stop; CLI event logs show no shell/file/patch tools. Evidence retained in `/tmp/tmr-live-20261021b`. This accepts the exercised single-node JavaScript sandbox loop, not arbitrary installed runtimes or complete Flow propagation.

## Linear sandbox Flow execution (2026-10-21)

`tl_preview_run_flow({workspaceId,startNodeId,inputs})` reads the exact persisted node/dependency/connection graph and returns the entire linear chain with node configurations, package references/permissions and initial inputs. The catalog now contains fifteen tools. The existing `tl_start_node_run`, `tl_get_node_run` and `tl_stop_node_run` accept the returned run plan/ID; local JSswift approval explicitly says Avvia Flow MCP and describes fail-fast propagation. It does not reuse the Agent Runtime trace-only runFlow.

`core/runtime/sandbox-flow-plan.cjs` is a pure narrow scheduling plan, not a replacement node engine. It requires an actual root, exact declared ports and connections in the same workspace, one outgoing edge per reachable node and one incoming edge per target. Branches/joins/cycles, unsupported control links and missing/disabled/foreign edges fail before execution. Every selected node must load through the existing installed sandbox-package authority. No untrusted client node definitions or inferred edge identities are accepted.

The existing McpRuntimeRuns coordinator snapshots topology, nodes and package/source identity. Start and each node invocation revalidate the reviewed fingerprint. Each sandbox uses the same Main-owned runner and permissions as single-node execution. Matching `emit` events propagate through the stored sourcePort/targetPort; RuntimeContract.applyConnectionMapping applies the existing mapping semantics. All original events, including other ports and mapping warnings, remain in per-step evidence. Multiple matching emissions each invoke the next node, without an MCP hardcoded cap. The initial adapter is sequential and isolated from renderer Event Bus dispatch so background subscribers cannot execute the same delivery twice. It does not claim general live-bus Flow scheduling.

Runs persist as kind mcp-flow-run with chain, complete steps (input, result, raw sandbox trace, failure, timestamps/duration) and deliveries (edge identities, original payload, mapping result/warnings and target input). Sandbox emits/logs additionally enter existing tl_events/tl_flow_logs with workspace/node/run/execution provenance. Channel records are not silently rewritten and background subscriptions are not triggered. A producer failure stops scheduling downstream work while retaining every output/diagnostic already returned; a cancelled run waits for actual active-sandbox termination. A completed invocation with no matching output has explicit terminal-attention evidence rather than inventing a terminal result. Source or package changes between steps stop further launches. Historical failures remain separate from later corrections.

Unit regressions verify 4→8→11, middle failure/retained correction, stale/unsupported topology, mid-chain cancellation, multiple emitted messages, retained non-routed facts and RuntimeContract mapping warnings. `test/tl-mcp-flow-electron.cjs` installs only a temporary QA package, invokes the official SDK client against production TL Main, confirms starts/config edits locally, executes actual sandboxes and verifies runtime history/events and physical stop. The last dialog-label correction is covered by that repeated Electron test. Integrated suite: 339 pass/two optional skips.

Real Codex external-client acceptance completed 28 MCP calls and six local approvals: success with step outputs 4/8/11; config.fail=true on double; failed Flow stopping after source/double with QA_MIDDLE_ERROR; reviewed config.fail=false; corrected success11 with old failure still readable; waiting double with live trace; stop producing cancelled with no add step or surviving sandbox. Independent read-only SQLite checks confirm four Flow records (3/2/3/2 steps), eight runtime events, ten logs, two config snapshots, final fail=false and unchanged node archive/topology. CLI events show no shell/file/patch tools. This was a dedicated temporary project, not the user's authorized test Flow. Evidence: `/tmp/tmf-live-20261021/independent-evidence.json`, CLI JSONL and run data. Arbitrary branching, fan-in semantics, cycles, non-sandbox nodes and in-place live-bus execution remain outside this accepted slice.
